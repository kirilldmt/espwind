# Как проверить API из вашей Wi-Fi-сети

Проверяйте с компьютера или телефона, подключённого **к той же домашней сети,
что и ESP32**. VPN только на компьютере, расширение браузера, Private Relay
или мобильный интернет могут дать другой результат. Если таблу нужен VPN,
его маршрут должен обеспечивать роутер.

Сайт Windy.app и его API — разные проверки. Открывающийся сайт ещё не доказывает,
что большой ответ прогноза загрузится целиком.

## Перед прошивкой: открыть API в браузере

Эти два адреса можно открыть прямо в новых вкладках:

- [Измерения KITEPITER](https://api.windyapp.co/v10/meteostations/getData/1chipru_840d8eaa9b63?predict=0&canWindNull=1&info=1).
- [Измерения PULKOVO](https://api.windyapp.co/v10/meteostations/getData/ULLI?predict=0&canWindNull=1&info=1).

Ожидается текст JSON: `"status":"success"` и непустой массив `response.data`.
Браузер может красиво форматировать JSON или показать его одной длинной строкой.
`timestamp` — время измерения в Unix-секундах, а не время открытия вкладки.

**Отдельно проверьте прогноз.** После скачивания или клонирования репозитория
откройте файл [check-api.html](check-api.html) обычным браузером на компьютере.
Например, на macOS из корня проекта:

```sh
open docs/check-api.html
```

Страница создаёт ссылку на прогноз для **текущей московской даты** и двух станций.
Нажмите «Открыть прогноз Крона» и дождитесь полной загрузки вкладки.
Успешный ответ содержит `status: success`, `response.timezone: Europe/Moscow`
и массив `response.forecast` с погодными строками. API может включить граничную
точку следующего дня; прошивка выбирает из ответа свои 192 часа.
Не используйте случайную старую ссылку с фиксированными `from_ts`/`to_ts`.

HTML-файл не делает фоновых запросов: он только открывает прямые ссылки в новых
вкладках. Поэтому ограничения CORS на чтение чужого сайта не искажают эту проверку.
Если открыли HTML через просмотрщик файлов телефона и ссылки не появились,
воспользуйтесь обычным браузером компьютера или локальным сервером:

```sh
python3 -m http.server 6465 --bind 127.0.0.1 --directory docs
```

Затем откройте **http://127.0.0.1:6465/check-api.html** на этом компьютере.
Сервер доступен только локально.

Если вкладка висит, ответ обрывается, появляется ошибка сети, 403 или 429,
проверка не пройдена. Повторять десятки раз подряд не нужно: 429 требует паузы.
Сравните одну и ту же проверку без VPN и с маршрутом через VPN на роутере.
Один успешный ответ не гарантирует круглосуточную стабильность.

## После подключения табло: проверить саму ESP32

1. Включите табло и подождите 30–60 секунд после подключения к домашнему Wi-Fi.
2. Откройте **http://wind64.local/api/status**. Если имя не находится, возьмите IP
   устройства из списка клиентов роутера и добавьте `/api/status`.
3. Проверьте поля:

| Поле | Ожидаемый результат |
| --- | --- |
| `connected` | `true`: есть подключение к Wi-Fi |
| `clockKnown` | `true`: известно корректное время |
| `forecastReady` | `true`: удалось разобрать прогноз |
| `kitepiterReady`, `pulkovoReady` | `true`: получены измерения |
| `polling[].lastHttp` | `200` у каждого источника |
| `polling[].successes` | Больше нуля |
| `polling[].consecutiveFailures` | `0` после успешного обновления |
| `stations[].error` | `false` после успешного обновления |

Готовность данных может остаться `true` после последующей ошибки: это сохранённый
кэш. Поэтому смотрите также последний HTTP-код, ошибки, возраст измерения и
счётчики. Источники обновляются по своему расписанию, а не при открытии страницы
статуса. `lastHttp: 0` при неудачной попытке может означать проблему DNS/TLS или
транспортный таймаут, а не HTTP-ошибку сервера.

`ЗАДЕРЖКА` и `УСТАРЕЛО` сами по себе не доказывают блокировку API: станция могла
прислать старое измерение при успешном HTTP 200. Важно время самой записи.

Не публикуйте ответ статуса целиком без очистки: он содержит `token` страницы
настроек и `ssid`. Для сообщения об ошибке достаточно версии прошивки,
HTTP-кодов, счётчиков, статусов и возраста данных.
